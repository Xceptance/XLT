# Modern XLT Reporting Engine: Unified Comparison, Trend, and Temporal Analytics

XLT introduces a modernized reporting architecture designed to transform performance analysis across both multi-run comparisons and single-run deep-dive analytics:

1. **Pillar 1: Performance Comparison & Trend Report**: Combines the previously separate **Diff Report** (2 runs) and **Trend Report** ($N$ runs) into a single, cohesive comparison engine powered by an **offline, deterministic natural language verdict engine**, modern enterprise visuals (light theme), interactive **Apache ECharts 6** data visualizations, and automated hotspot detection ("Top Movers").
2. **Pillar 2: Modernized Single-Run & Requests Temporal Analytics**: Overhauls the traditional single-run report through a **Top Pageable Chart Workbench + Bottom High-Density Long Table** layout ("Split Inspector without Split"), preserving unhidden temporal behavior over time while delivering instant client-side sorting, filtering, and deep diagnostics across all 1,000+ endpoints simultaneously with zero DOM lag.

---

## 1. Motivation & Core Principles

Traditional comparison and diff reports often overwhelmed engineers with hundreds of rows of raw percentage deltas without answering the 5-second question: **"Did performance improve, degrade, or stay flat, and where?"**

The new reporting architecture addresses this through four core principles:

1. **Unification**: Comparing 2 runs ($A \text{ vs } B$) is treated as the $N=2$ case of comparing $N$ runs. Users no longer have to choose between two separate reporting tools.
2. **Executive-First Hierarchy**: The top of the report provides a clear verdict, sanity check, key KPI delta cards, and top bottlenecks before diving into detailed tables.
3. **100% Offline & Deterministic**: The report requires **no web server, no external network, and no cloud/LLM APIs**. It opens directly via `file:///` in any browser.
4. **Interactive Visualizations**: Replaces static image charts with interactive client-side Apache ECharts (percentile distribution overlays, multi-axis progression curves).

## 2. Deterministic Natural Language Verdict Engine (Zero-LLM)

A standout capability of the new report is the top-level **Executive Verdict Banner** and **Diagnostic Narrative**:

```
[⚠️ PASS WITH CAPACITY NOTICE] System scaled 2.0x throughput cleanly, but error volume spiked +113%

Under 200% target load (22k orders/hr peak), aggregate transaction latency improved slightly 
(-6.9% mean, -5.4% P95), demonstrating solid web-tier elasticity. However, authentication and 
cart actions suffered connection pool contention, driving error count from 902 up to 1,925 
(+1,023 errors). Subsequent runs (#13 and #15) successfully cleared this pool contention.
```

### Why Deterministic Rules Instead of an LLM?

While XLT can export structured data for LLM analysis (see [`ai-data.md`](file:///home/rschwietzke/projects/GIT/XLT.report-update/doc/feature-doc/ai-data.md)), the core executive summary inside the report itself is **100% generated by deterministic Java rules**:

- **Zero Network / Offline**: Runs locally in isolated test environments, air-gapped CI/CD systems, and offline laptops.
- **Zero Hallucinations**: Every claim, metric, and percentage is mathematically verifiable against the raw test records.
- **Instant**: Synthesizes the full narrative in under **5 milliseconds** during report generation.
- **Auditable & Reproducible**: Re-running the report in 6 months produces the exact same verdict, making it reliable for automated CI/CD deployment gates.

### How the Natural Language Engine Works

The engine operates as a 4-step diagnostic pipeline:

```
+-------------------------------------------------------------+
| 1. Metric Delta Calculation                                 |
|    Throughput Δ%, Mean Latency Δ%, P95 Δ%, Error Count Δ    |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 2. Multi-Dimensional Classification (Decision Tree)        |
|    Evaluate Load Scaling, Latency Stability, Error Spikes  |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 3. Hotspot Identification (The Root Cause)                  |
|    Find the #1 regressed transaction, request, or error     |
+-------------------------------------------------------------+
                              │
                              ▼
+-------------------------------------------------------------+
| 4. Deterministic Sentence Synthesis                         |
|    Populate grammatical templates with data & test metadata |
+-------------------------------------------------------------+
```

#### Step 1: Metric Delta Calculation
The backend extracts and compares summary statistics between Baseline (A) and Comparison (B):

$$\Delta \text{Throughput} = \frac{\text{Throughput}_B - \text{Throughput}_A}{\text{Throughput}_A} \times 100$$

$$\Delta \text{Latency} = \frac{\text{Mean}_B - \text{Mean}_A}{\text{Mean}_A} \times 100$$

$$\Delta \text{Errors} = \text{Errors}_B - \text{Errors}_A$$

#### Step 2: Multi-Dimensional Classification
The rule engine categorizes the run across three dimensions:

| Dimension | Evaluation Logic | Example Classification |
| :--- | :--- | :--- |
| **Load Scalability** | $\Delta \text{Throughput} \ge +50\%$ | `SCALED_CLEANLY` ($2.0\times$ load) |
| **Latency Behavior** | $\Delta \text{Mean} \le 0\% \land \Delta P95 \le 0\%$ | `IMPROVED_OR_STABLE` |
| **Stability / Errors** | $\Delta \text{Errors} > 100 \lor \text{ErrorRate}_B > 1.0\%$ | `DEGRADED_SPIKE` |

From these states, the decision matrix determines the overall status:
- **🟢 `PASS`**: Throughput maintained/improved, latency within $\pm 5\%$, error rate flat or reduced.
- **🟡 `PASS_WITH_NOTICE`**: Throughput scaled and latency stable, but error rate increased or minor tail inflation observed.
- **🔴 `REGRESSION`**: Throughput degraded ($> -5\%$), latency increased ($> +10\%$), or major SLA thresholds breached.

#### Step 3: Hotspot Identification
The engine queries the transaction, action, and request sets to pinpoint the exact driver of the change:
- **Worst Latency Jump**: $\max(\Delta \text{Mean ms})$ or $\max(\Delta \text{P95 ms})$ $\rightarrow$ e.g., `SetStore_CA_FR_CartPage` (+29.2%).
- **Worst Error Spike**: $\max(\text{Errors}_B - \text{Errors}_A)$ $\rightarrow$ e.g., `TAccountLogin` (+71 errors) and `TAddToCart` (+64 errors).

#### Step 4: Grammar Template Synthesis
The final headline and narrative are constructed using parameterized grammar templates that combine the classifications, calculations, and the engineer's configured `<reportComments>`:

**Headline Template:**
```
"System scaled {load_ratio}x throughput cleanly, but error volume spiked {error_pct}%"
```

**Narrative Template:**
```
"Under {target_load_context}, aggregate transaction latency {latency_verb} " +
"({mean_delta}% mean, {p95_delta}% P95), demonstrating solid {tier} elasticity. " +
"However, {hotspot_components} suffered {issue_type}, driving error count from " +
"{base_errors} up to {target_errors} (+{error_delta} errors)."
```

## 5. Technical Architecture & Offline Portability

To ensure 100% offline portability without browser CORS restrictions when opening `file:///` URLs:

1. **Data Delivery via `js/data.js`**:
   The Java generator packages comparison metrics into a self-contained JavaScript data structure (`window.XLT_DATA = { ... };`). The HTML file references this script directly, avoiding blocked `fetch()` or `XMLHttpRequest` calls on local files.
2. **Client-Side Rendering**:
   Lightweight vanilla JavaScript dynamically binds data to DOM components, handles instant filtering/sorting, and updates ECharts instances when the user selects different runs or toggles views.
3. **CLI & CI/CD Compatibility**:
   - `create_diff_report.sh <run1> <run2>` invokes the unified generator in 2-run Diff mode.
   - `create_trend_report.sh <run1> <run2> <run3> ...` invokes the unified generator in Multi-Run Trend mode.
   - Both commands remain fully backward-compatible with existing CI/CD automation.

# Part II: Modernized Single-Run Reporting & Requests Temporal Analytics

While comparison reporting answers *"what changed between runs"*, single-run reporting answers the foundational question: **"how did the system behave over time during this specific test?"**

In high-concurrency enterprise load tests with 1,000+ distinct HTTP endpoints, engineers need both **high-resolution temporal behavior** and **instant multi-column searchability** without sacrificing performance or readability.

---

## 6. Core Design Philosophy: Preserving Visual Ground Truth

### A. The Primacy of Behavior Over Time
In performance testing, aggregate scalar numbers (such as average latency or median) often hide critical runtime phenomena:
- **Micro-bursts & GC Pauses**: A request with a 215ms average may experience 12-second spikes every 10 minutes due to JVM garbage collection or database checkpointing.
- **Connection Pool Exhaustion**: Scatter plots showing individual request runtimes immediately reveal stepped plateaus when thread pools saturate.
- **Warmup & Cold-Start Effects**: Time-series charts clearly distinguish initial JIT compilation or cache-warming delays from steady-state performance.

> [!IMPORTANT]
> **"The quality of the old reports is that one sees the requests behavior easily because the images are not hidden."**
> In the modernized reporting architecture, temporal charts are **never killed or buried behind deep accordion clicks**. They remain front and center at full resolution.

### B. "Load All at Once" vs. Pagination
Traditional modern web apps often rely on pagination ("Load More" or 50 rows/page). For performance engineers, this approach is fundamentally flawed:
- Sorting by "Slowest P95" or "Highest Hourly Volume" must evaluate the **entire dataset of all 1,065+ endpoints simultaneously**, not just the current page.
- Engineers scan global outliers across the entire run in one sweep.

The modernized report delivers **instant, zero-DOM-lag rendering of all 1,000+ endpoints simultaneously** using lightweight vanilla JavaScript and clean tabular DOM structures.

### C. Hourly Throughput (`1/h`) as a First-Class Metric
In production e-commerce and enterprise applications, capacity and business SLAs are negotiated in hourly volumes (e.g., *"100,000 orders/hour"*, *"250,000 catalog searches/hour"*). 

The new report elevates **`1/h` (`countPerHour`)** to a primary headline metric alongside traditional requests-per-second (`1/s`), both in the top workbench and as a dedicated sortable table column.

---

## 7. Architecture: Top Chart Workbench + Directory Table + Continuous Chart Stream

The single-run timer pages (`transactions.html`, `actions.html`, `requests.html`, `agents.html`, `custom-timers.html`, `custom-values.html`) use a three-zone vertical layout:

1. **Top Sticky Chart Workbench** (wrapped with the directory table inside `<div class="workbench-scope">`): stays pinned while scrolling and inspecting rows in the directory table, then naturally unsticks once the engineer scrolls past the table into the Continuous Chart Stream.
2. **High-Density Directory Table (`#directory-section`)**: renders all endpoints/timers simultaneously with dedicated columns for labels/methods, dynamic percentiles, dynamic runtime segmentation, and a duration-agnostic **`Trend`** sparkline.
3. **Below-Table Continuous Chart Stream (`#stream-section`)**: a full-width single-column stream directly below the directory table so engineers can scroll down past the table and glance through all charts in table sort/filter order.

### Components of the Architecture:

1. **Top Chart Workbench (`#workbench-section`)**:
   - Dedicated inspection station pinned above the table while within `.workbench-scope`.
   - Instant multi-tab switching (`Overview`, `Moving Averages`, `Count/s`, `Concurrent Users`, `Arrival Rate`, `Response Size`, plus on-demand `Dynamic Overview (Zoom)` powered by ECharts 6 and `charts/*/*.json`).
   - Live headline KPI strip (`1/h`, `1/s`, `Mean`, `P95`, `Errors / Events`) and diagnostic footnote strip.

2. **High-Density Directory Table (`#directory-section`)**:
   - Renders all rows at once for global multi-column sorting and boolean substring filtering (`foo bar -baz | qux`).
   - **Dedicated `Labels` and `Method` Columns**: Keeps badge pills in their own columns so timer/endpoint names align cleanly down a vertical axis.
   - **Duration-Agnostic `Trend` Sparklines**: Inline 20-bucket SVG response-time sparkline per row (`Trend range: <min> – <max> ms` tooltip), scaled across the actual test window regardless of whether the run is 15 minutes or 3 hours.
   - **View Jump Buttons**: `📌 Top Workbench` and `📊 Continuous Stream` smoothly scroll between the top workbench and the below-table stream without hiding either section.

3. **Below-Table Continuous Chart Stream (`#stream-section`)**:
   - Full-width single-column cards (`grid-template-columns: 1fr`) synchronized with the directory table's active sort order and filter query.
   - Sticky stream toolbar with global **Glance Metric** tab switcher (`data-stream-tab`) and `⬆ Table` jump button.
   - Each card displays rank, labels/method badge, full un-truncated name, URL pattern subtitle, inline key metrics, per-card chart tabs, `⬆ Table` row jump, and `Inspect ↗` (which loads the item into the Top Workbench).
   - **1,000+ Endpoint Performance Guardrails**: Inserts cards in batches of `24` via `IntersectionObserver` (`rootMargin: "800px"`) with manual `Load Next 24` / `Load All Remaining` fallback controls, native `loading="lazy" decoding="async"` on images, and CSS `content-visibility: auto; contain-intrinsic-size: auto none auto 480px;` on `.stream-card`.

## 8. Interaction Ergonomics: Zero-Jitter & Zero-Scroll Engineering

Paging through over 1,000 requests requires strict attention to physical interaction ergonomics. Rapid paging must feel crisp, tactile, and completely stable under the user's cursor.

### A. Mathematical Zero-Jitter Pager Layout
The workbench header uses a strictly constrained 3-column CSS Grid:

```css
.workbench-header {
  display: grid;
  grid-template-columns: minmax(280px, 380px) 340px minmax(0, 1fr);
  align-items: center;
  gap: 16px;
}
```

- **Left Column (`minmax(280px, 380px)`)**: Constrained with `overflow: hidden; text-overflow: ellipsis;` and native `title` tooltips.
- **Center Pager Track (`340px`)**: Rigidly locked in place (`74px` Prev + `174px` tabular-nums counter + `74px` Next) so `◀ Prev` and `Next ▶` never shift horizontally when clicking through 1,000+ items.
- **Right Column (`minmax(0, 1fr)`)**: Allocates remaining horizontal space to KPI metrics and controls (`🔗 Link`, `📌 Pinned`, `▲ Hide Chart`).

### B. Zero-Scroll Navigation Model
- **Chart Paging (`Next ▶`, `◀ Prev`, `←`, `→`)**: Updates chart imagery, metrics, and table selection class with `scrollIntoView = false`.
- **Table Keyboard Navigation (`↑`, `↓`)**: Navigates table rows with `scrollIntoView = true`, keeping the active row visible.
- **Inline Diagnostic Drawers (`Enter` Key or `▸` Row Expander)**: Expands percentile distributions, socket/network timing breakdowns, distinct URL counts, and clickable sample URLs directly beneath the active row.

# Part III: Dynamic Modern Load Report Specification (Java-to-JS Data Bundle Approach Alongside Classic XSLT)

This specification defines how XLT builds the new Single-Run Modern Load Report using a dynamic Java-to-JS data bundle architecture (`config/testreport-modern/` + `js/*-data.js`) **without replacing or modifying the existing XSLT 1.0 report rendering** (`config/xsl/loadreport/*.xsl` and `config/testreport/`) or changing `bin/create_report.sh`.

## 9. Architectural Goals & Coexistence Strategy

### A. UI Mode Property in `reportgenerator.properties` (`modern` default, `classic` intact)
XLT keeps the existing XSLT 1.0 report rendering completely intact alongside the new JS-driven report, controlled via a standard property in [`config/reportgenerator.properties`](file:///home/rschwietzke/projects/GIT/XLT.report-update/config/reportgenerator.properties) while `bin/create_report.sh` (`.cmd`) stays completely unchanged:

```properties
## Report UI generation mode:
## - modern  ... JS data-bundle report using config/testreport-modern (default)
## - classic ... classic XSLT 1.0 report using config/testreport and config/xsl/loadreport
com.xceptance.xlt.reportgenerator.ui = modern
```

- `bin/create_report.sh` and `bin/create_report.cmd` remain unchanged; like any other report generator property, `com.xceptance.xlt.reportgenerator.ui` is read via `ReportGeneratorConfiguration` (and can be overridden via `-Dcom.xceptance.xlt.reportgenerator.ui=classic`).
- To modernize an already generated output report directory without re-running `create_report.sh` on raw timer logs, an extra standalone script (`bin/update_report_ui.sh` / `bin/update_report_ui.cmd`) runs just the modern UI template + JS data-bundle generation step.
- **Scope of Phase 1**: Single-Run Load Report (all 15 HTML pages + `scorecard.html` + `ai-data.md`). Diff and Trend report generators remain on their existing pipeline until Phase 2.

### B. Static Template Directory Layout
- **Classic assets**: Remain untouched in [`config/testreport/`](file:///home/rschwietzke/projects/GIT/XLT.report-update/config/testreport) and [`config/xsl/loadreport/`](file:///home/rschwietzke/projects/GIT/XLT.report-update/config/xsl/loadreport).

  - `*.html`: 16 static, 100% data-driven HTML shells (`index.html`, `transactions.html`, `actions.html`, `requests.html`, `slowest-requests.html`, `custom-timers.html`, `custom-values.html`, `page-load-timings.html`, `web-vitals.html`, `agents.html`, `errors.html`, `events.html`, `network.html`, `external.html`, `configuration.html`, `scorecard.html`) containing zero hardcoded test numbers or project names.
  - `css/style.css`: Unified light/dark design system and print stylesheet.
  - `images/`: XLT logos and icons (`xlt-logo.svg`, `favicon.svg`, `favicon.png`).
  - `js/`: Static client scripts (`theme.js`, `nav.js`, `workbench.js`, `chart-lightbox.js`, `dynamic-chart.js`, `table-copy-markdown.js`, `echarts-6.0.0.min.js`, and lightweight page renderers `overview-page.js`, `errors-page.js`, `events-page.js`, `slowest-requests-page.js`, `network-page.js`, `config-page.js`, `external-page.js`, `scorecard-page.js`).

## 10. Generation Pipeline & Standalone CLI

### A. Single Source of Truth: `testreport.xml` + `scorecard.xml` + `charts/*/*.json`
Rather than coupling JS serialization to internal in-memory `DataProcessor` state, the Java data generator (`ModernReportGenerator`) reads from the artifacts produced in `<outputDir>`:
1. **`<outputDir>/testreport.xml`**: All aggregated statistics, `<general>`, `<summary>`, `<configuration>`, `<testReportConfig>`, `<transactions>`, `<actions>`, `<requests>`, `<slowestRequests>`, `<customTimers>`, `<customValues>`, `<pageLoadTimings>`, `<webVitalsList>`, `<agents>`, `<errors>`, `<events>`, `<responseCodes>`, `<requestMethods>`, `<contentTypes>`, `<hosts>`, `<ips>`, `<customLogs>`, and `<external>`.
2. **`<outputDir>/scorecard.xml`** (when present): Scorecard evaluation result, group/rule statuses, points, and messages.
3. **`<outputDir>/charts/<section>/<chartBase>.json`** (when charts are enabled): Time-series JSON files produced by [`BasicTimerDataProcessor.java`](file:///home/rschwietzke/projects/GIT/XLT.report-update/src/main/java/com/xceptance/xlt/report/providers/BasicTimerDataProcessor.java#L521), downsampled into 20-bucket `spark` arrays for table sparklines and loaded on-demand by ECharts zoom.

### B. Execution inside [`ReportGenerator.java`](file:///home/rschwietzke/projects/GIT/XLT.report-update/src/main/java/com/xceptance/xlt/report/ReportGenerator.java)
1. **Stages 1–3 unchanged**: `readLogs(...)` $\rightarrow$ `createReport(outputDir)` (writes `testreport.xml`, `charts/*.webp`, `charts/*/*.json`, `csv/`) $\rightarrow$ `evaluateReport(xmlReport)` (writes `scorecard.xml`).
2. **Stage 4 (`transformReport` & `transformScorecard`)**:
   - If `ui == classic`: executes existing `config/testreport/` copy and XSLT 1.0 transformations.
   - If `ui == modern`:
     1. Copies static templates from `config/testreport-modern/` to `<outputDir>` (excluding `scorecard.html` if `scorecardXml == null`).
     2. Runs `ModernReportGenerator.generateDataBundles(xmlReport, scorecardXml, outputDir, config)` to emit `js/report-meta.js` and all `js/*-data.js` files.
     3. Still generates **`ai-data.md`** (via `config/xsl/loadreport/ai-data.xsl` or direct writer) so LLM summary markdown remains available.
   - In [`ReportGenerator.updateScorecard()`](file:///home/rschwietzke/projects/GIT/XLT.report-update/src/main/java/com/xceptance/xlt/report/ReportGenerator.java#L701): if `<outputDir>/js/report-meta.js` exists (or `ui == modern`), regenerates `js/scorecard-data.js`, updates the scorecard status in `js/report-meta.js`, and copies `scorecard.html` from `config/testreport-modern/`.

### C. Standalone UI Regeneration Script (`bin/update_report_ui.sh` / `.cmd`)
To allow fast (~1 second) iteration and upgrades on existing report directories without re-parsing gigabytes of raw `timers.csv` agent logs:
- **Scripts**: `bin/update_report_ui.sh <reportDir>` and `bin/update_report_ui.cmd <reportDir>`.
- **Entry Point**: `com.xceptance.xlt.report.UpdateReportUiMain`.
- **Behavior**:
  1. Verifies `<reportDir>/testreport.xml` exists.
  2. Copies current static templates (`*.html`, `css/`, `js/`, `images/`) from `config/testreport-modern/` into `<reportDir>`.
  3. Parses `<reportDir>/testreport.xml`, optional `<reportDir>/scorecard.xml`, and `<reportDir>/charts/*/*.json` to write fresh `js/report-meta.js` and `js/*-data.js` bundles.

## 11. JavaScript Data Packaging & Schema Contract

To prevent unrelated pages from downloading the multi-megabyte request catalog (`requests-data.js` is ~2.7 MB on a 1,065-request test) while remaining 100% compatible with `file:///` execution (where `fetch()` is blocked by CORS), data is split into **one small shared metadata script (`js/report-meta.js`)** plus **per-page data scripts (`js/*-data.js`)** loaded via `<script src="...">`:

| Script File | Global Variable | Consumed By | Source XML / Files |
| :--- | :--- | :--- | :--- |
| `js/report-meta.js` | `window.XLT_META` | All 16 `.html` pages (`nav.js`, `workbench.js`) | `<general>`, `<summary>`, `<testReportConfig>`, section counts, `scorecard.xml` summary |

## 12. Full XLT Feature Parity Requirements

All existing XLT report features from `config/xsl/loadreport/*.xsl` and [`config/reportgenerator.properties`](file:///home/rschwietzke/projects/GIT/XLT.report-update/config/reportgenerator.properties) must be faithfully supported:

### A. XLT Labeling Rules (`<labels>`)
In XLT, [`LabelingRuleProcessor`](file:///home/rschwietzke/projects/GIT/XLT.report-update/src/main/java/com/xceptance/xlt/report/labelingrules/LabelingRuleProcessor.java) assigns a whitespace-delimited `labels` string (`TimerReport.labels`) to transactions, actions, and requests in `testreport.xml` (`<labels>guest checkout</labels>`).
- **No synthetic category guessing**: The generator must **not** invent categories from timer names. It reads the `<labels>` element from `testreport.xml` and serializes `labels: ["guest", "checkout"]` (or `labels: []` when empty).
- **When no labels are defined across a page**:
  - No label badges are displayed on rows, in the Top Workbench, or in the Continuous Stream.
  - The directory label filter chip bar is hidden (or omitted), and the `Labels` table column is hidden so no empty column wastes horizontal space.
- **When labels are defined on one or more rows**:
  - A dedicated **`Labels`** column is rendered in the directory table.
  - Rows with **1 or 2 labels** display each label as a `.label-chip` pill.
  - Rows with **3 or more labels** display the first 2 `.label-chip` pills plus a hoverable `+N` badge (`.label-chip-more`) listing all remaining labels in a tooltip/popover (matching [`config/xsl/loadreport/util/timer-labels.xsl`](file:///home/rschwietzke/projects/GIT/XLT.report-update/config/xsl/loadreport/util/timer-labels.xsl)).
  - The directory filter bar displays clickable label chips (`All`, plus each distinct label with its matching row count) and the search input (`matchesXltFilter`) matches against both timer `name` and all `labels`.
- **HTTP Method Column on `requests.html`**:
  - On `requests.html`, HTTP method (`GET`, `POST`, etc., if present in request naming/URL or metadata) is distinct from `<labels>`: `<labels>` uses the `Labels` column and label filter chips.

### B. Dynamic Percentile & Runtime Segmentation Columns (`<testReportConfig>`)
Users can configure custom percentiles (`com.xceptance.xlt.reportgenerator.runtimePercentiles`) and custom runtime segmentation intervals (`com.xceptance.xlt.reportgenerator.runtimeIntervals`) in `reportgenerator.properties`, which XLT serializes into `<testReportConfig>` in `testreport.xml`:
- **Dynamic Percentile Columns**: Each timer item stores a `percentiles` map (`{ "p50": 210.0, "p95": 270.0, ... }`) matching the `<percentiles>` child elements in `testreport.xml`. `workbench.js` dynamically builds the `Percentiles [ms]` column group from `window.XLT_META.testReportConfig.runtimePercentiles`.
- **Dynamic Runtime Segmentation Columns (`requests.html`)**: Each request item stores `segmentation: [{ count: 3527, pct: 100.0 }, ...]` from `<countPerInterval>` and `<percentagePerInterval>`. `workbench.js` dynamically builds the `Runtime Segmentation` column group from `window.XLT_META.testReportConfig.runtimeIntervals`.

### C. Request Table Colorization Rules (`<requestTableColorization>`)
XLT supports rule-based cell background colorization on `requests.html` via `com.xceptance.xlt.reportgenerator.requests.table.colorization.*` (serialized as `<colorizationGroupName>` on each `<request>` and `<requestTableColorization>` under `<testReportConfig>`):
- For each request row, `workbench.js` looks up `item.colorizationGroup` (falling back to `"default"` if present) in `window.XLT_META.testReportConfig.requestTableColorization`.
- Applies the same green $\rightarrow$ neutral $\rightarrow$ red linear interpolation as `config/xsl/loadreport/util/colorize.xsl` to `mean`, `min`, `max`, `percentile` (`id="p50"`, etc.), and `segmentation` (`id="1000"`, etc., including inverted logic on non-last intervals) cells, adapted cleanly for both light and dark themes.

### D. Action Apdex Scores (`<apdex>`)
On `actions.html`, each `<action>` in `testreport.xml` contains `<apdex threshold="1.0" ActionGroup="default">0.985</apdex>`:
- Serialized as `apdex: { value: 0.985, threshold: 1.0, group: "default" }`.
- Rendered in a dedicated sortable `Apdex` column in `actions.html` with standard XLT Apdex color coding (`convert-apdex-to-color.xsl` parity) and threshold tooltip.

### E. Result Browser Links (`resultBrowsers/`) & Custom Data Logs (`custom_data_logs/`)
- **Errors (`errors.html`)**:
  - Each `<error>` in `testreport.xml` includes `<count>`, `<message>`, `<testCaseName>`, `<actionName>`, `<requestName>`, `<detailChartId>`, `<trace>`, and `<directory>` entries (pointing to dumped Result Browser directories under `resultBrowsers/<dir>/index.html`).
  - When `linkToResultBrowser` is enabled and `<directory>` entries exist, `errors.html` renders direct clickable links to open the corresponding Result Browser snapshot(s), plus transaction/action/request error detail charts (`charts/errors/*.webp`).
  - If `<customLogs>` entries exist, renders links to `custom_data_logs/`.
- **Slowest Requests (`slowest-requests.html`)**:
  - Renders all fields from `<slowestRequests>` (`runtime`, `time`, `name`, `requestId`, `url`, `httpMethod`, `responseCode`, `contentType`, `bytesSent`, `bytesReceived`, `dnsTime`, `connectTime`, `sendTime`, `serverBusyTime`, `receiveTime`, `timeToFirstBytes`, `timeToLastBytes`, `usedIpAddress`, `ipAddresses`), plus baseline comparison against the matching aggregate `<request>` (`mean`, `p95`).

### F. External Data (`external.html`), Page Load Timings, and Web Vitals
- **`external.html`**: Dynamically renders custom external tables and charts from `<external>` in `testreport.xml` (`ExternalReportGenerator`).
- **`page-load-timings.html` & `web-vitals.html`**: Use the workbench/table engine when `<pageLoadTimings>` / `<webVitalsList>` contain data, and render a clean empty-state card when empty.
- **Navigation Empty-State Indicators**: `nav.js` reads `window.XLT_META.counts` and `window.XLT_META.scorecard` to display live count pills on `Errors`, `Agents`, and `Scorecard` (`PASSED`/`FAILED`), and dims or marks empty optional sections in the `More ▾` menu.
